Retail Demand Forecasting with AI

A store-level demand forecasting system for multi-branch retail. A gradient-boosted model predicts each store's daily sales up to 30 days ahead, validated walk-forward against a naive baseline, and a GenAI layer turns the forecast into plain-language, store-specific recommendations for operations teams. Orchestrated with Dagster.

View on GitHub

At a glance

Dataset
Rossmann Store Sales (public, 1,115 stores), with a bundled synthetic sample that runs the full pipeline offline
Model
Gradient-boosted regression (HistGradientBoostingRegressor) over calendar, lag, and rolling features
Validation
Walk-forward holdout: the last 30 days per store, with MAE, RMSE, and MAPE
Accuracy
MAE 223.4, RMSE 312.8, MAPE 6.2%
Baseline
44.8% lower MAE than a naive lag-7 forecast
Horizon
30-day daily forecast per store, produced iteratively
Insight layer
An LLM converts forecasts into store recommendations, with a fully offline heuristic fallback
Orchestration
Dagster job: engineer, train, evaluate, forecast, insights. Python, pandas, scikit-learn

Pipeline

Sales history → Feature engineering → Gradient-boosted model → Walk-forward validation
                  → 30-day forecast per store → GenAI insights

What I built

  • Feature engineering. Calendar features (day of week, month, weekend, holidays), promotion and school-holiday flags, and lag plus rolling-window statistics that capture weekly seasonality and recent store momentum.
  • One model across stores. A single gradient-boosted regressor trained on all stores, using store type as a categorical feature, so each store borrows strength from the others.
  • Walk-forward evaluation. The last 30 days per store are held out and scored with MAE, RMSE, and MAPE, compared against a naive lag-7 baseline so the score has a reference point.
  • Iterative horizon forecast. Because future lags are unknown, the model feeds on its own predictions to produce a 30-day daily forecast per store without observed future sales.
  • GenAI insight layer. An LLM writes the briefing an operations lead would otherwise write by hand, turning forecast numbers into store-specific guidance; without an API key, a fully offline heuristic produces the same report shape.
  • Orchestration. A Dagster job wires the stages together so the pipeline runs as one production-shaped unit.

Decisions worth noting

  • Why walk-forward, not a random split. A time series must be validated on a future window. A random split leaks future information into training and inflates the score, which is the most common way forecasting projects fool themselves.
  • Why a naive baseline. A lag-7 carry-forward is the bar any forecast has to clear. Reporting the improvement over it keeps the result honest and readable to a non-specialist.
  • Why the forecast feeds on itself. At prediction time the future lags do not exist, so the model uses its own previous predictions. The alternative, assuming the last lag holds constant, is simply a worse model.
  • Why a GenAI layer at all. A forecast is only useful if someone acts on it. The insight layer closes the gap between a numeric output and a decision an operations lead can make.

Honest notes

This is a portfolio project, not a production deployment. The model is not served behind an API or retrained on a schedule; what it demonstrates is the modelling, validation, and evaluation discipline.

The data is public. The pipeline targets the Rossmann Store Sales dataset, and ships a synthetic sample with the same schema so reviewers without Kaggle access can run it end to end.

The metrics shown are from the bundled sample. Real-dataset numbers differ once the Kaggle download is used; the pipeline and the evaluation logic do not change.

The GenAI layer is optional. It calls an OpenAI-compatible model when a key is present and otherwise falls back to a deterministic heuristic, so the pipeline is never blocked on an external API.
