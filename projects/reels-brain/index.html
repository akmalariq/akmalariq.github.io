Case study · Retrieval-augmented generation & multimodal extraction

Reels Brain

Nobody re-watches the Reels they save. They pile up, and the useful knowledge — a gluten-free recipe, a styling trick, a Hanoi coffee shop spotted in a caption in Vietnamese — is stranded in a video nobody opens again. This turns that pile into a searchable, source-linked archive. Speech recognition and vision OCR read what a Reel actually says, a structuring pass turns it into typed JSON without dropping the detail, and a chat answers strictly from the archive, citing the IG account and the Reel's original release date.

At a glance

The problem
Saved Reels pile up as video and are never opened again; the knowledge inside them is stranded
Why it is hard
A Reel's content lives in three places at once — speech, on-screen text, and the caption — and any one alone loses it
Extraction
ASR (asr-1.0) for speech, a vision model reading sampled frames for on-screen text, plus the caption, all stored verbatim
Detail preservation
Structured JSON is a view over the raw extraction; the original ASR/OCR/caption stays reachable so nothing is flattened away
Grounding
Chat answers only from retrieved chunks and refuses rather than inventing; every claim carries a numbered citation
Provenance
Every item and answer links back to the IG account, Reel URL, and original release date, not ingest time
Retrieval
Hybrid: cosine over MiniMax embo-01 embeddings fused with SQLite FTS5 keyword search
Runtime
FastAPI + SQLite (WAL) + yt-dlp + ffmpeg, React & TypeScript
Security
scrypt password sessions behind Cloudflare Access; the public demo is read-only on synthetic data
Tests
28 passing, including an HTTP-level assertion that every data route rejects an anonymous request

Pipeline

Reel URL / file → yt-dlp download → ffmpeg audio + frames → ASR + vision OCR → Structured JSON → Embeddings → Grounded chat

What I built

  • Three-channel extraction. The on-screen text is the part most pipelines miss, because a recipe Reel states its quantities as burned-in captions while the audio is just music. Audio is downmixed to mono 16 kHz for the ASR API, frames are sampled and de-duplicated with a perceptual hash to keep the vision bill bounded, and all three channels are kept separately.
  • Structured output that does not eat the detail. An LLM pass turns the merged text into typed JSON — recipe, hack, travel, or other — with ingredients, quantities, steps, tips and substitutions. The prompt contract forbids summarising away specifics, and the raw transcription is never overwritten, so the structured view can be regenerated from the source rather than repaired by hand.
  • Grounding as a hard rule. A question retrieves chunks first; if retrieval is empty the model is instructed to say the answer is not in the archive. The refusal path is verified: with an empty archive the API returns a grounded-refusal response, not a 500 and not a plausible invention.
  • Provenance on every surface. Author, Reel URL, and the IG release date ride along with each source and are attached to items, consolidated guides, and chat citations, and the library sorts by release date so the archive reads chronologically the way it was saved.
  • Topic consolidation. Reels are grouped into topics (for example a gluten-free collection) and an LLM merges them into a single written guide that unifies ingredients and steps, keeps conflicting variations visible rather than picking one, and annotates every section with the source it came from.
  • Retrieval without a vector database. At personal scale a numpy cosine scan over stored embeddings, fused with SQLite FTS5, is instant and removes a native dependency; the MiniMax embeddings endpoint is isolated behind one client so a local model can replace it.
  • Cost-bounded ingestion. Long jobs run on a background worker that reports progress, records failures with the real error, and supports reprocessing from the failed stage. A downloadable private Reel is handled by uploading the file instead of scraping.

Security model

The archive holds a personal media library and an API key, so exposing it needed a real answer rather than a disclaimer. There are two deployments with deliberately different postures.

  • Private instance, two layers. Cloudflare Access authenticates the person at the edge with an emailed one-time code, and the application independently requires a session cookie on every data route. Either layer alone would be the only thing standing between the archive and a stranger; both together mean reaching the origin directly still returns a 401.
  • Passwords are hashed with scrypt from the Python standard library, sessions are HMAC-signed with a twelve-hour expiry, and failed logins are rate limited per client address so the password cannot be guessed by repetition.
  • The public demo cannot be written to. It runs against a synthetic dataset with invented accounts, captions and reel ids. Ingest, upload, reprocessing, item edits, topic changes and consolidation are all refused, which means a visitor cannot alter the archive or spend a cent of model credit.
  • The demo and the archive never share a database. Seeding the demo wipes and recreates its own data directory. The real archive is never the source for anything published.

Decisions worth noting

  • Why OCR is not optional. Running speech recognition alone would have silently dropped the exact quantities that make a recipe usable, because on a Reel they are written on screen, not spoken. Vision OCR on sampled frames is the part that makes the archive actually complete.
  • Why the raw text is immutable. The structuring pass is a projection. Keeping the raw ASR/OCR/caption verbatim means a bad extraction can be re-derived and a prompt can be improved and re-run, instead of the only copy being the model's lossy summary.
  • Why the model refuses. A system that answers a recipe question from general knowledge is worse than useless here — it looks right and is unsourced. Retrieval is checked before generation, and an empty result is reported as “not in the archive”.
  • Why not a hosted vector store. The archive is one user's and small. Storing embeddings as blobs in SQLite and scanning them with numpy removes an external service, its cost, and a moving part, with no measurable retrieval cost at this size.

Honest notes

This is a personal tool, not a product. It runs for a single user with no accounts and no multi-tenancy. The saved-Reel archive, the IG cookies, and the model API key all live on one machine by design.

The source is private. The repository is not published. It holds prompts and fixtures taken from a real personal archive, and the extraction layer sends audio and video frames to a third-party model API, so the code is described here rather than linked.

The public demo is a different posture. What is deployed is a read-only instance on synthetic data, not the real archive: ingest and every write endpoint are refused, so a visitor cannot mutate anything or spend model credits. The private instance it is modeled on requires a password session on every API route, with scrypt hashing and rate limiting, behind Cloudflare Access at the edge.

Extraction quality follows the models. ASR and vision OCR are only as good as the underlying models, and a Reel that is mostly music with burned-in text will lean heavily on the OCR path. Reels that cannot be downloaded anonymously are supported by uploading the file, not by scraping around Instagram's access control.

The consolidation is a rewrite. The merged topic guide is generated text over real sources, with citations to each Reel, but it is a summarisation step and not a substitute for reading the source when a recipe matters.
