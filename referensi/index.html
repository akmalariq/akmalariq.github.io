1. Orleans — Distributed Virtual Actors

MSR-TR-2014-41 · 2014 · engineering

Mechanism. An actor is *virtual*: always addressable by id, instantiated on demand, deactivated when idle, re-instantiated elsewhere after failure. One turn at a time per activation, so no locks. At-least-once messaging, eventual single activation.

Taken. The per-key promise queue in tabel and studio (one session, one turn), and the rule that an entity's own state is cacheable while shared truth is not. Ignored. The runtime. One box and SQLite already serialise.

2. The Multicore Server Challenge

repo · 2026 · engineering

Mechanism. 127 submissions, same 8-core box, Postgres on the same machine, no caching across requests, score = users held for 5 minutes at p95 < 500 ms. Best: 230k users; Postgres still eats ~50 % of the box.

Taken. Count round trips, not lines of code — tabel's EDA went from ~500 DuckDB processes to 2 queries (SUMMARIZE + one batched corr), 3.4 s → 122 ms. Ignored. epoll/io_uring. Our box does ~4–6k rps; we need hundreds.

3. Tinycharts — a skill, not a SaaS

site · tweet · product design

Sources. tinycharts · launch tweet

Mechanism. A Claude skill that turns "how does X work" into one hand-drawn isometric HTML sheet. What makes it worth $34.90: a real statechart behind the buttons — disallowed moves are refused with a reason. 9 types free, 28 paid. Sells a ZIP, not a server.

Taken. The "legend is the product" idea went into tabel's chart cards (mapping + query), and the tone of kurator. Ignored. The drawing kit; that is months of taste, not a weekend.

4. Painted Houses — a painting rebuilt as a house

site · design

Mechanism. Four paintings, each turned into an isometric building in the painting's palette, with a legend that maps the elements (turban → pantile roof, pearl → gable window). No 3D library: SVG, one fixed camera, one fixed light, painter's algorithm by hand.

Taken. Every chart in tabel now carries its mapping in words, not only a picture. Ignored. Hand-built isometric scenes; too expensive for a data tool.

5. Details.so — taste as an MCP

details.so/mcp · distribution product

Source. details.so/mcp

Mechanism. A curated UI library (3,500+ references, code in a "Vault") exposed as a remote MCP server with OAuth (Supabase) and credit metering (X-Details-Credits-*). Sold with every paid plan. Install is one command per client.

Taken. The product shape for kurator: a narrow, curated, callable library with opinions and a jangan list. The positioning: *"your AI can generate, but it doesn't know what good looks like."* Ignored. OAuth and credits at this scale; a bearer token and a rate limit are enough until strangers depend on it.

6. ClairEmu — Linux in the browser

emu.kadcom.dev · design engineering

Mechanism. Debian 13 on RISC-V 64 in the browser via TinyEMU + WebAssembly; COOP/COEP and SharedArrayBuffer; WebGPU ("Suar · Vulkan"), WebGL ("Pelita · OpenGL"), 2D canvas; CRT/STN screen effects; five languages; explicit "beta, your data may be lost".

Taken. Renderer choice as a user-facing control instead of a hidden fallback; honesty in the beta banner. Ignored. Client-side compute. Our work is small; the server is the right place for it.

7. The exact-match-domain play

tweet · distribution

Mechanism. Register bestaidatalabs.com, publish *"Best AI Data Labs | Zeton Reference"*, get it indexed in days, and watch Google's AI Overview quote your own verdict back to the buyer. 0 → 7 figures claimed in 10 days (almost certainly pipeline, not revenue).

Taken. The legitimate half: name the buying query in the H1, answer it in the first sentence, compare honestly against named competitors, date the claims. That became rampung.akmalariq.dev/jasa-payroll. Ignored. The EMD farm. One algorithm update ends it, and for payroll it reads as astroturf.

8. How AI search actually retrieves

thread · distribution engineering

Mechanism. Google's Discovery Engine exposes the pipeline: prepare → retrieve → signal → serve, with seven signals (base ranking, Gecko embeddings, Jetstream cross-attention, BM25, PCTR, freshness, boost/bury), chunks capped at ~500 tokens, ancestor headings travelling with chunks, and three independent structured-data flags: searchable, indexable, retrievable. (The screenshot in the tweet is actually ChatGPT's Sonic classifier: no_search_prob, complex_search_prob, thresholds.)

Taken. Write in self-contained, quotable blocks with question-shaped headings; keep one claim per chunk. This is also why an MCP beats a page: the agent asks directly. Ignored. SEO folklore that contradicts the pipeline.

9. Sprite stacking — 2D that turns like 3D

Kimo's post · how-to · fofr's reply · design motion

Sources. Kimo · fofr · SpriteCook

Mechanism. One flat slice per pixel of height, stacked 1 px apart, all rotated by the same angle — any view from one small sheet. Cut slices from four orthographic views (top/side/front/ back); squash 0.75 for a lower camera. Pitfalls: jitter, soft art smears, holes fill in.

Taken. studio is built on the same constraint: the model produces a grid, the server validates every cell and renders it — small, checkable, cheap.

Built. studio's Stack view (2026-11-18): one flat slice per height, drawn 1 px apart, all turned by the same angle; squash 0.60–1.00; height 3–10; PNG, 24-frame turntable GIF, and slice-sheet export. Two sources: a generated top-down sprite with height derived from silhouette + luminance (approximate), or an uploaded slice sheet from SpriteCook/MagicaVoxel (exact). The four-view carving script is *not* implemented — studio has one grid, not an image pipeline. Ignored. Rotating the stack; our sprites rotate in the game engine, not in the generator.

10. The "motion studio in N repos" list

Mechanism. Twenty-one open-source libraries (Remotion, Motion Canvas, Anime.js, Three.js, Tone.js, FFmpeg…) framed as "skills". The best reply in the thread is the real lesson: *"None of these check the output."*

12. Minicharts — numbers drawn as things

april-zhu.com/minicharts · design data

Mechanism. Give it numbers; it draws the chart as a real object from your subject — a pie chart as a pie of coins, a waterfall as a waterfall — hand-drawn, to scale, touchable. Same look as Tinycharts, different job: this one is data, not process.

Taken. The bar for tabel's charts: a chart is a *communication choice*, not a rendering choice. The mapping line (departemen → rata-rata gaji · 3 titik) is our cheap version of the same idea. Ignored. Subject-aware illustration. It needs an art kit per domain; our charts must work for any table.

13. Colorfigures, iso-figure, statechart-art — the lineage

Colorfigures · iso-figure · @q_micke's painting outfits · design product

Mechanism. A skill built on another skill built on a free primitive: iso-figure draws isometric objects, Colorfigures adds ink/marker/colour and playable states, Painted Houses composes both. Every layer credits the one below — MIT where required, inspiration where not.

Taken. Crediting is part of the product: our kurator lists the references that shaped it, and studio's README names its lineage. It costs nothing and buys trust. Ignored. Building the illustration engine; we buy depth in one narrow direction instead.

14. The SpriteCook how-to

spritecook.ai/blog/sprite-stacking-pixel-art · design motion

Mechanism. The reproducible half of the sprite-stacking tweet: cut one slice per row from four orthographic views (top/side/front/back), stack 1 px apart, rotate all slices, squash 0.75 for a lower camera. Numbers that matter: 15 slices of 24×43 px; 1 px spacing; 10× draw scale.

Taken. The constraint we copied into studio: a text model returns a grid, the server validates every cell, the renderer only draws. Small format, checkable output. Ignored. Slice carving from images — we generate the grid directly and skip photography.

15. The content factory is a kanban board

tweet · 2026-11-16 · product distribution video

Mechanism. *"Video editing is following the same path AI coding took in 2025–26. The 10×–100× programmers don't write code anymore. They build software factories."* The screenshot is the claim made concrete: a board for a kids' puppet show — 107 items, stages Idea → Script → Voicing → QC → Kit ready → Approved → Partly posted → Posted, 80 approved and waiting, 14,441 views tracked, one fully finished. The asset is not the video; it is the pipeline that turns an idea into a posted short without a meeting.

The second image is the adoption curve: video ~9 months behind code, dotted line crossing above today's point.

Taken. Honestly: not built yet, and it names the gap. studio makes one artefact per prompt — sprite, loop, ASCII, stack — then forgets it. There is no queue, no review state, no record of what was exported or where it went. The board says the product is the *batch*: draft → generated → approved → exported → shared, with a platform check per item. That is the next feature, not this one.

Ignored. The niche and the volume (puppets, 100+ episodes). Volume without a channel is inventory; we have no channel to feed.

Patterns that keep repeating

  1. Taste is the product; the callable interface is the distribution. Details, Tinycharts,

HorizonX, Scrolltide — all sell curated judgment, wrapped so an agent can consume it.

  1. Constraint is style. One camera, one light, one grid, one palette. Painted Houses and

sprite stacking both buy coherence by refusing generality.

  1. Check the output. The best reply to the motion list, and the reason tabel/studio

validate every cell and every SQL statement.

  1. Do less work per unit of state. Orleans (turns), multicore (round trips), and our EDA

rewrite all point the same way.

  1. Write for retrieval. 500-token blocks, question headings, one claim each — or be an MCP

and skip retrieval entirely.
